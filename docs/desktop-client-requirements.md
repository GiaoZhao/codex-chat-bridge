# Desktop Client Requirements

状态：已确认的产品需求基线

最后更新：2026-08-02

## 1. 背景

Codex Chat Bridge 当前以命令行方式运行。它已经能够连接 QQ Gateway、监听本机 Codex
任务、通过 QQ 继续任务并推送结果，但普通用户仍需手工编辑配置、打开终端并判断进程
是否存活。Bridge 核心已经写入轮转 JSONL 日志，但普通用户仍缺少持续可见的运行状态、
日志查看和诊断包导出入口。

Desktop Client 的目标是消除这些使用和运维门槛，而不是增加新的聊天入口。

## 2. 产品定位

Desktop Client 是 Codex Chat Bridge 的本地配置与运行控制台。

它负责：

- 首次配置和后续设置维护。
- 启动、停止、重启和后台驻留 Bridge。
- 展示 Bridge、QQ Gateway 和 Codex 的运行状态。
- 持久保存并展示日志。
- 管理登录后自动启动和运行期间的系统防睡眠能力。
- 在网络恢复或系统唤醒后自动恢复桥接连接。

它不负责：

- 提供聊天输入框或完整聊天界面。
- 替代 QQ、Codex Desktop 或 Codex CLI。
- 在本地展示或编辑完整对话历史。
- 把 `/threads`、`/use`、`/new` 等 QQ 操作复制成一套本地任务管理产品。
- 绕过 Codex 的审批、沙箱或权限控制。

QQ 仍是远程交互入口，Codex 仍是任务执行与本地完整记录入口。Desktop Client 只管理
桥接本身。

## 3. 目标用户与体验

目标用户不应被要求理解 Python、虚拟环境、Shell、PowerShell、环境变量或 Thread UUID。

第一版应满足：

- Windows 和 macOS 用户通过安装包完成安装。
- 应用内完成配置，不手工编辑 `.env`。
- 应用内选择初始 Codex 任务，不手工查询或输入 UUID。
- 日常使用不需要打开终端。
- 关闭主窗口后 Bridge 继续在系统托盘或菜单栏运行。
- 发生停止、断线或错误时，用户可以直接看到状态和日志。

## 4. 功能需求

### 4.1 首次配置

配置向导至少包含：

- QQ Bot AppID 和 AppSecret。
- QQ 绑定状态、绑定码生成和重新绑定入口。
- Codex CLI 自动发现、版本检查和可执行状态。
- Codex 本地任务索引与会话目录检查。
- 从可见根任务列表选择初始任务和工作目录。
- QQ 通知、附件限制和其他现有 Bridge 配置。
- macOS Desktop 刷新开关及风险说明。
- 运行时保持系统唤醒开关。
- 登录后自动启动开关。

已有 `.env` 和 `data/state.json` 时，应提供兼容读取或一次性迁移，不能要求现有用户重新
绑定。

### 4.2 生命周期控制

客户端必须提供：

- 启动 Bridge。
- 停止 Bridge，并等待正在执行的任务安全结束。
- 明确确认后强制停止当前任务。
- 重启 Bridge。
- 关闭窗口后最小化到系统托盘或 macOS 菜单栏。
- 从托盘快速查看状态、打开主窗口、启动、停止和退出。
- 可配置的登录后自动启动。
- Bridge 工作线程异常退出后的自动恢复，并记录退出原因和重试过程。

“退出客户端”和“关闭主窗口”必须是两个明确动作。只有退出客户端才停止后台 Bridge。

### 4.3 运行状态

状态页至少展示：

- Bridge：未启动、启动中、运行中、停止中、已停止、异常。
- QQ Gateway：未连接、连接中、已连接、重连中、错误。
- Codex CLI：已发现、不可用、执行中、空闲。
- 当前任务标题和项目名称；UUID 只在诊断详情中显示。
- 当前远程任务队列数量。
- 当前监控的可见根任务数量。
- Bridge 启动时间和持续运行时间。
- 最近一次 QQ 入站、结果推送、Gateway READY、断线和重连时间。
- Desktop 刷新功能状态及最近一次结果。
- 系统保持唤醒状态。
- 客户端和 Bridge 版本。

状态必须来自 Bridge 的结构化事件或状态快照，不能通过解析面向用户的打印文本推断。

### 4.4 日志与诊断

客户端必须：

- 将 Bridge、QQ Gateway、worker、会话监听、Desktop 刷新和电源事件写入持久日志。
- 使用带时间、组件、级别和阶段的结构化日志。
- 支持日志轮转和容量上限，防止长期运行无限占用磁盘。
- 在界面中按时间、级别和组件查看与筛选日志。
- 提供一键导出诊断包。
- 导出时脱敏 AppSecret、访问令牌、绑定码、`openid`、本地路径和其他凭证。
- 明确显示日志目录和最后写入时间。
- Bridge 异常退出时保留 traceback，不得只显示“启动失败”。

默认日志保留天数、单文件大小和文件数量在技术设计阶段确定，并允许后续配置。

### 4.5 现有 Bridge 能力保留

引入客户端后，以下现有远程能力必须保持不变：

- QQ 私聊文字继续当前 Codex 任务。
- QQ 图片作为 Codex 图片输入。
- 安全的 Codex 本地结果图片回传 QQ。
- Markdown 卡片、快捷按钮和纯文本降级。
- `/threads`、`/use`、`/current`、`/new`、`/status`、`/recent`、`/cancel` 和 `/help`。
- 当前任务执行期间的消息排队。
- 所有可见根任务的最终结果通知。
- guardian、subagent 和已归档任务过滤。
- QQ 绑定和非绑定用户拦截。
- macOS Desktop 刷新能力及安全降级。

这些能力继续由 QQ 和 Bridge 提供，客户端只显示相关配置和运行状态。

## 5. 电源与后台运行需求

### 5.1 已确认边界

用户接受以下系统限制：

| 系统状态 | 预期行为 |
| --- | --- |
| 显示器息屏 | Bridge 继续运行 |
| 系统锁屏 | Bridge 继续运行 |
| 系统因空闲准备睡眠 | 客户端在启用保持唤醒时阻止系统睡眠 |
| 用户主动选择睡眠 | 允许 Bridge 离线，唤醒后自动恢复 |
| 笔记本合盖并触发睡眠 | 允许 Bridge 离线，开盖唤醒后自动恢复 |
| 系统休眠、关机或断电 | Bridge 无法运行 |
| 系统重新登录 | 在启用自动启动后恢复 Bridge |
| 网络中断 | 显示断线并持续重连 |
| 网络恢复或系统唤醒 | 无需人工操作，自动重建 Gateway 连接 |

客户端不承诺在操作系统真正睡眠、休眠、关机或断电时保持在线。要求这些状态下持续在线
必须使用不会睡眠的常开电脑，本项目不通过修改危险的系统级策略绕过该限制。

### 5.2 macOS

- 当前命令行版本已使用 `caffeinate -i` 阻止空闲系统睡眠。
- 客户端应使用等价的系统电源断言，并允许显示器正常息屏。
- 断言只在 Bridge 运行且用户开启保持唤醒时存在。
- Bridge 停止或客户端退出时必须立即释放断言。
- 普通 Mac 笔记本合盖触发的睡眠不在保活承诺范围内。

### 5.3 Windows

- 客户端应使用 Windows 官方电源请求能力阻止空闲系统睡眠，例如
  `SetThreadExecutionState(ES_CONTINUOUS | ES_SYSTEM_REQUIRED)` 或等价 API。
- 不使用 `ES_DISPLAY_REQUIRED`，屏幕应能正常关闭。
- 用户主动睡眠、休眠和系统配置的合盖动作优先于 Bridge 保活。
- 停止 Bridge 或退出客户端时必须清除电源请求。

### 5.4 恢复处理

客户端必须记录系统挂起和恢复事件。系统恢复后应主动验证 Gateway 状态；不能确认连接
有效时，应关闭旧连接并重新获取连接状态。恢复和重连过程必须显示在状态页并写入日志。

持续防睡眠会增加笔记本耗电，设置页和首次启用时必须给出明确提示。

## 6. 安全需求

- AppSecret 不在界面、普通日志、异常提示或诊断包中明文展示。
- 发布版优先使用 macOS Keychain 和 Windows Credential Manager 保存 AppSecret。
- 非敏感配置使用明确的版本化配置格式，并支持迁移。
- 本机调试端口只能连接回环地址。
- 不提供远程切换沙箱、审批或危险权限的能力。
- 日志导出前执行脱敏，原始本地日志由用户明确选择后才能分享。
- 自动启动使用当前用户权限，不要求管理员或系统级服务权限。

## 7. 跨平台交付

第一版目标交付物：

- macOS `.app`，发布阶段可进一步提供 `.dmg`。
- Windows 用户级安装包或可执行程序。
- 安装包内置 Python 运行时和应用依赖。
- 保留现有 CLI 入口，用于开发、测试和无界面运行。
- Windows 和 macOS 分别构建、测试和发布，不能假定一个构建产物跨平台运行。

推荐技术路线为 Python + PySide6 + PyInstaller，因为现有 Bridge 核心可以直接复用。
该选择优先降低开发和维护成本，不以最小安装包体积为首要目标。Electron、Tauri 或重写
后端不属于第一版方案。

## 8. 建议架构

第一版使用单个托盘应用进程：

- GUI 主线程负责窗口、托盘和用户操作。
- Bridge 在受控后台线程中运行。
- Application Controller 管理启动、停止、重启、异常恢复和状态聚合。
- Bridge 通过结构化事件回调更新状态模型。
- 统一日志组件同时写入轮转文件和界面日志流。
- 平台适配层处理密钥库、登录启动、电源断言和系统恢复事件。

这一方案能解决终端关闭、窗口关闭和 Bridge 工作线程异常的问题，同时保留较低的第一版
成本。独立系统服务、守护进程和跨进程 IPC 暂不作为第一版前提；只有后续证明单进程托盘
应用无法满足可靠性时再拆分。

## 9. 验收标准

### 9.1 通用

- 新用户无需安装 Python 或使用终端即可完成配置并启动 Bridge。
- 已有用户可以迁移现有配置和绑定状态。
- 关闭主窗口后 Bridge 继续运行，托盘状态正确。
- 启动、停止和重启不会产生重复 Bridge 实例。
- Bridge 工作线程异常时，界面显示原因、保存 traceback，并按策略自动恢复。
- AppSecret 和访问令牌不会进入普通日志或诊断包。
- 引入客户端后，现有 Bridge 自动化测试和 QQ 功能保持通过。

### 9.2 电源与恢复

- macOS 和 Windows 在显示器息屏或锁屏时保持 Bridge 运行。
- 开启保持唤醒后，空闲超时不会让系统自动睡眠。
- 关闭保持唤醒后，系统电源行为恢复为用户原有设置。
- 用户主动睡眠或合盖后允许离线；唤醒后 Bridge 自动恢复连接。
- 网络断开和恢复不要求用户手动重启客户端。
- 所有电源切换和连接恢复事件均可在日志中追踪。

### 9.3 可观测性

- 状态页能够区分进程停止、Gateway 断线、Codex 不可用和 worker 执行失败。
- 当前运行状态与日志中的最新事件一致。
- 日志跨应用重启保留，并受到容量上限约束。
- 用户可以在不提供 `.env` 的情况下导出可用于排查的脱敏诊断包。

## 10. 第一版排除项

- 本地聊天界面。
- 完整会话历史阅读器或编辑器。
- 本地复制全部 QQ 命令的任务管理界面。
- 多聊天平台适配器；架构可预留，但第一版仍只支持 QQ。
- 自动更新。
- 云端托管和跨设备同步。
- 系统真正睡眠期间保持在线。
- 未公开的 Codex Desktop IPC 或数据库写入。
- Windows Desktop 自动刷新承诺；现阶段继续默认关闭。

## 11. 实施阶段与成本

### 阶段一：可观测性与生命周期

- 结构化状态事件。
- 持久轮转日志。
- Application Controller。
- Bridge 启停、异常恢复和电源断言。

### 阶段二：Beta 客户端

- 配置向导、状态页、日志页和托盘。
- 配置迁移和系统密钥库。
- macOS 与 Windows 打包。
- 跨平台功能测试。

朋友可用的 Beta 预计约 6-10 个开发人日。

### 阶段三：公开稳定发行

- macOS 签名与公证。
- Windows 代码签名和安装体验完善。
- 发布自动化、升级策略和更完整的兼容性测试。

包含公开发行准备的总成本预计约 10-15 个开发人日。该估算不包含多聊天平台、自动更新
和完整聊天产品。

## 12. 已确认决策

- 客户端只做 Bridge 配置、运行控制、状态监控和日志，不做聊天。
- QQ 和 Codex 继续承担远程交互及完整任务体验。
- 支持显示器息屏和锁屏时持续运行。
- 运行期间可以阻止系统因空闲自动睡眠。
- 接受主动睡眠、合盖、休眠、关机和断电期间 Bridge 离线。
- 系统唤醒、网络恢复或重新登录后自动恢复 Bridge。
- 第一版优先低开发成本和跨平台可靠性，不追求最小安装包体积。

## 13. 待后续确认

- 客户端最终产品名称、图标和品牌视觉。
- 第一批交付是仅供朋友测试的未签名 Beta，还是直接准备签名公开发行。
- 登录后自动启动的首次默认值。
- 日志默认保留天数和容量。
- 是否在后续版本加入自动更新。
